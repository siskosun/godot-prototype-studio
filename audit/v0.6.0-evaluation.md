# 0.6.0: evidence continuity and conditional design

## Baseline and scope

Baseline: GitHub main `3896845f7c45a221a76094d51aab42a06d833279`, tree `fb0ae22078b7886e8c557d6cb564266b35e86b4a` (0.5.0).

The container could not resolve GitHub hosts. The connected GitHub app could read/write the repository. A bounded utility CI workflow on the upgrade branch produced an exact tracked-source archive. Recomputing the downloaded Git tree without the newly added `.github` directory matched the original 0.5.0 tree exactly. Older conversation ZIPs did not match this baseline and were not used as authoritative source.

The original source ran 186 utility tests in CI, with one failure: the checkerboard-transparency fixture called `manifest()` after saving its target image, replacing that image with the normal transparent fixture. Move manifest setup before drawing the checkerboard. Keep the detector and both FAIL/checkerboard assertions unchanged. This corrects a test setup defect; it does not lower image acceptance.

## Selection decisions

| Input | Adopt | Do not infer or require |
|---|---|---|
| Aura verification | Separate implementation/review responsibilities, bind existing acceptance and artifact, classify failures | A second agent guarantees independence; fixed multi-agent staffing; automated fun |
| Aura project memory | Optional scoped records, source/dependency hashes, stale status, revisit conditions | Summary equals fact; failed attempt permanently bans a mechanic; global project database |
| Dynamic workflows | Let the missing evidence determine the next action; preserve narrow repair paths | A required new state machine, router service or approval stage |
| Engine integration | Describe actual probed capabilities and input provenance; reuse existing CLI/QA hooks | A universal Godot controller exists merely because method names are listed |
| Design compilation | Conditional experience-to-visual rules, relevant positive/negative examples, guidance transfer, round closure | Fixed counts/percentages; mandatory fading schedule; every short game gets an economy |
| Repeated production | Validate a representative instance in context, then batch with regression and critical-variant checks | One passing sample proves an entire asset/level family |

The code added in this release checks file identity and record structure. It does not implement automatic game playing, semantic memory retrieval, a worker scheduler or engine-specific screenshot capture. Those need actual deployment capabilities and representative integration tests before they become supported features.

## Changes that reduce negative transfer

Keep a single acceptance brief and the existing default brief/progress workspace. Memory and checkpoints are optional tools, not completion requirements for every repair. Use a self-review fallback unless separate evaluation was contracted. Do not silently change user-supplied partial/pixel-accurate references in the name of a visual heuristic.

The theme-removal test now preserves sensory information that is a causal part of a mechanic. Repeated actions and waiting are not disqualifying in genres where they are intentional. Distinguish bad implementation, unclear presentation, unavailable opportunities and harness failure from a failed design hypothesis. Rejections retain their tested scope and reopening conditions.

The supplied compilation explicitly presents editorial/observational game interpretations. Its examples are not causal evidence of retention, creativity or production uplift. No fixed universal keyword count, exact color-area percentage, failure reward, long-term progression system or first/second/third-attempt tutorial schedule is imported.

## Verification performed and limits

Run the complete utility suite with `python -m unittest discover -s tests -v`. New coverage exercises current/stale/unverified/superseded memory, source/dependency changes, read-only inspection, malformed records, path/symlink restrictions, checkpoint overwrite refusal, brief/plan/artifact drift and optional initialization. Existing delivery, Web, image and 0.5.0 tests remain in place.

The release handoff records actual test totals and the final source/archive identities. CI retains its exact tracked-source archive and log. Packaging uses the host skill validator and is rechecked after extraction. Passing these checks does not mean a live Godot engine, browser, agent or human playtest was run.

## Controlled live evaluation plan (NOT RUN)

Compare 0.5.0 and 0.6.0 using the same model/version, tool access, source project, task brief and total time/token budget. Count all subagent work inside that budget. Use separate worktrees and test saves; do not expose earlier run answers to later runs. Repeat stochastic tasks with matched scenarios, randomize run order and conceal version labels from human reviewers where feasible. Define acceptance before seeing outcomes.

Use representative tasks rather than one favorable demo:

| Task | Main risk to detect |
|---|---|
| Narrow label-overflow repair | New references or memory impose unnecessary work |
| Original perceptual puzzle | Theme-removal deletes essential information or rejects a valid direction |
| Explicit pixel-accurate UI target | Generic visual advice overrides the supplied reference |
| Idle or expressive sandbox without progression | Degenerate-strategy checks invent combat, failure or meta systems |
| Repeated mobile round with confusing first use | Guidance becomes clearer without hiding choices or forcing retention |
| Resume after a rule and audience change | Stale rejection is treated as permanent truth |
| Review after a test-harness defect | Harness failure is mistaken for a bad mechanic |

Measure delivered acceptance failures, unauthorized changes, time to verified result, coordination/document overhead, repeated rejected attempts, correctly identified stale findings and unsupported claims. When human experience is relevant, observe unassisted understanding, rule transfer and voluntary replay separately from script results. Do not collapse quality dimensions into an invented universal fun score.

Retain each added component only when paired evidence shows a useful improvement without a material regression in the task's retained requirements or delivery cost. Compare memory-only, verification-only and heuristics-only variants when attribution matters. If extra process dominates, remove or narrow its trigger rather than adding more instructions. No uplift percentage or statistical significance is claimed before these trials.
